## Deviations from the proposal: all sound

1. **Cache path -> project-local `graphify-out/`, redirected via `GRAPHIFY_OUT` (DEV 1).** The proposal's NOTE explicitly required Phase 1 to confirm the cache path and correct the manifest if it differed; it did differ, and the implementer used the confirmed `GRAPHIFY_OUT` env redirect - which is precisely the "output-dir redirect cleaner than a gitignore" the proposal's Open Questions hoped for. Faithful to intent. Sound.

2. **Index command `graphify update <path>` (DEV 2)** and **3. MCP via `graphify-mcp` console script (DEV 3).** Both empirically confirmed against the installed wheel. Consistent everywhere: manifest option descriptions, install.sh MCP registration and hook, README usage and options table. I grepped for stale `graphify --update` and stale `~/.cache/graphify`-as-container-target references and found none.

4. **Fixed `/var/cache/graphify` mount target instead of per-user `~/.cache/graphify` (DEV 4).** This is the deviation worth the most scrutiny, and it holds up:
   - **Forced, not chosen.** A feature's `containerEnv` is baked as a raw Docker `ENV`, and `${containerEnv:HOME}` (a devcontainer.json-level variable) does not resolve in that context - the first attempt failed the build with `unsupported modifier (:H)`. A fixed path is the correct response.
   - **Ownership is correct for the lace norm.** install.sh `chown`s `/var/cache/graphify` to the single remote user; the `non_root_user` scenario proves the remote user owns and can write it. A second non-root user in the same container would collide, but lace's one-project/one-user-per-container norm makes this a non-issue, and the README documents the single-shared-cache consequence.
   - **Actually cleaner than the sibling pattern.** claude-code and neovim target `/home/${_REMOTE_USER}/...`, which the proposal itself flagged as diverging from the `/root` script branch for a root remote user. The fixed `/var/cache/graphify` target eliminates that root-vs-non-root divergence entirely, and `/var/cache` is the standard FHS location for a regenerable cache. `recommendedSource` stays `~/.cache/graphify` on the host, so the host-side ergonomics match the siblings.
   - **Mount declaration is functional.** I confirmed lace namespaces a feature mount as `${shortId}/${mountName}` (`packages/lace/src/lib/template-resolver.ts:218`), so this manifest's `mounts.index` resolves to the label `graphify/index` - exactly what the README's settings-override example references. The label satisfies lace's `^[a-z0-9_-]+/[a-z0-9_-]+$` validator (`mount-resolver.ts:47`). No bug.

## Findings

### Non-blocking

1. **[non-blocking] README `> NOTE:` callouts lack attribution.** The three bare `> NOTE:` blocks in the README (mount section) omit the `NOTE(author/workstream)` attribution the writing conventions specify. Sibling READMEs are informal too, so this is cosmetic, but adding `NOTE(opus/code-graph/graphify-lace-feature)` would match the convention.

2. **[non-blocking] Git-hook sets a GLOBAL `core.hooksPath`, which shadows repo-local `.git/hooks`.** When `installGitHook=true`, `git config --global core.hooksPath ~/.config/git/hooks` disables any repo-provided hooks for that user across every checkout, not just adds a post-commit. The hook is opt-in (default off) and non-fatal, so the blast radius is bounded, but the README's option description ("adds latency to every commit") understates it - it also overrides other repos' hooks. Worth a one-line README caveat. Untested by any scenario (honestly flagged), so no correctness claim rests on it.

3. **[non-blocking] pipx re-install idempotency is untested.** `pipx install graphifyy==<ver>` on an already-populated `PIPX_HOME` can exit non-zero ("already installed"). This never fires in a normal single-pass feature build (fresh layer), so it is not a real failure mode here, but if a future consumer re-runs install.sh over an existing `/usr/local/pipx` it could surface. A `--force` or a pre-check would harden it. Low priority.

4. **[non-blocking] MCP happy-path remains the one meaningful untested behavior.** Not required for this iteration, but a follow-up scenario pairing `installMcpServer=true` with the claude-code feature and asserting `claude mcp list` reports `graphify` would close the last real coverage gap. Track as future work, not a blocker.
