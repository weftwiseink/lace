BLUF

Lace is becoming the outer wrapper around the devcontainer CLI, not a guest nested inside .devcontainer/devcontainer.json. Three checklist clusters were each sent out for independent analysis; all three read as pieces of that one move.

Prebuild removal is the keystone: it deletes the two source-mutation write sites (prebuild.ts, restore.ts) that otherwise complicate both remaining workstreams, and it removes prebuild.lock / prebuild/ from the .lace/ layout question entirely. It should land first.

Config‑home and .lace/up both then touch .lace/ naming and both reference the generated .lace/devcontainer.json path — they collide if done blindly in parallel and need a coordinated call on where that file lives before either proceeds.

1 · Prebuild removal → 2 · .lace/up layout + 2 · Config home (coordinated, not parallel-blind)

Prebuild removal

source-mutation complaint · rethink_prebuild
remove

Verdict: already decided by an accepted proposal the codebase never finished executing. Resume at Phase 3; a new design would duplicate work the deletion already subsumes.

  1. 00Close the weftwise verification gap: SSH + in-container tool smoke test, resolve whether sshd:1 is still needed
  2. 03Survey & migrate remaining projects (backup, clauthier, dotfiles, whelm, lace's own devcontainer)
  3. 04Delete ~800–1000 LoC: commands/{prebuild,restore,status}.ts, lib/{prebuild,restore,status,dockerfile,metadata,lockfile}.ts, plus branches in up.ts and 6 other files
  4. 05Test surface update: delete 7 prebuild-only test files, trim 8 partial ones, add the cache-reuse regression scenario
  5. 06Docs: rewrite docs/prebuild.md as a migration note, strip README prebuild sections
  6. 07Dogfood & ship: migrate lace's own devcontainer, full suite on 3 flagship projects, clean up lace.local/* images

Traps / open questions

Container-side SSH and tools were never smoke-tested on the one project actually migrated. Cache hygiene under partial edits was only measured cold-vs-warm. Empirical timing (234s/16s) hasn't been re-run since May — cheap insurance before resuming.

.lace/up layout

.lace/* scatter → .lace/up/
cleanup

Verdict: layout cleanup, not a behavior change — but two traps need a designed answer, not an incidental side effect of a rename.

  1. 01Design the merge-coordination mechanism: read-merge-write vs. a shared accumulator
  2. 02Point laceDir at .lace/up/; every relative() rewrite gains one ../
  3. 03Merge ports, mounts, runtime fingerprint (+ resolved-mounts, pending scope) into lace-resolutions.json
  4. 04Move logs/ under .lace/up/logs/
  5. 05Update debug-footer.ts's printed paths
  6. 06Update docs/architecture.md's settings-and-state section
  7. 07Legacy-file cleanup on first up after upgrade
  8. 08Update the 10 test files that reference these paths by string
  9. 09Reconcile sibling proposal 2026-03-07-lace-up-output-organization.md

Traps / open questions

The relativity fix is one line, but a missed call site fails silently until a local feature or custom Dockerfile build actually runs. Three independent writer classes each do a blind whole-file overwrite today; pointed at one filename without coordination, the later writer clobbers the earlier one's section on every run.

Config home

customizations.lace.* → .lace/lace.jsonc
needs proposal

Verdict: matches a gap the codebase already flagged (README's own "may no longer be sensible" note), but the devcontainer field has three candidate semantics with materially different cost, so phase one is writing the proposal, not the code.

  1. 01Proposal: resolve the devcontainer field (path-reference / inline-generates-source / inline-never-writes-back) and the .lace/ naming collision
  2. 02Centralize config-path discovery: 3 duplicated + 2 caller-supplied path sites
  3. 03Introduce .lace/lace.jsonc parsing, dispatch-only, no merge with the old shape
  4. 04Migrate ~15 extract*() call sites across 9 files to the new top-level shape
  5. 05Resolve the image-field rewrite write path in prebuild.ts / restore.ts
  6. 06Build a lace migrate-config one-shot command
  7. 07Update the lace init RFP to target the new file
  8. 08Documentation: README config sections, docs/architecture.md pipeline diagram

Traps / open questions

A hand-authored .lace/lace.jsonc would sit in the same directory as the existing generated, gitignored .lace/devcontainer.json: a direct contradiction of what .lace/ is documented to mean. No option removes VS Code's or CI's hard requirement for a real file at the conventional .devcontainer/devcontainer.json path.
